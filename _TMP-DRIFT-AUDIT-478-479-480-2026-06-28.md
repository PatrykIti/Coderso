H3. TASK-480 widget data contracts still disagree about raw data vs wrapper
entries.

Evidence:

- `_docs/_TASKS/TASK-480-02-L02-Data-Source-Registry-And-Service.md:102-114`
  defines `DashboardWidgetData` as display-ready data with no `id` and no `data`
  wrapper.
- The same file returns `{ id: widget.id, ...resolved }` from
  `resolveWidgetData()` at `:249-260`, contradicting the type comment that the
  widget id lives on `DashboardWidget`, not on the data payload.
- `_docs/_TASKS/TASK-480-02-L03-Contract-Tests.md:172-188` expects
  `{ id, type, data: ... }` and reads `out.data`, which no longer matches the
  display-ready union in L02.
- `_docs/_TASKS/TASK-480-03-L03-Widget-Data-Route.md:92-116` defines route
  entries as `{ id, type, status, data }` and then reads `resolved.data`.
- `_docs/_TASKS/TASK-480-04-L01-Widget-Renderer-Registry.md:141-152` expects
  `DashboardWidgetHost` to receive `state={{ status: "ready", data:
  DashboardWidgetData }}`.
- `_docs/_TASKS/TASK-480-05-L01-Widget-Grid-And-Edit-Mode.md:238` calls
  `<DashboardWidgetHost widget={w} editing={editing} />` without the required
  `state`.
- `_docs/_TASKS/TASK-480-05-L02-Add-Widget-Catalog-And-Configure-Panel.md:184`
  calls `<DashboardWidgetHost widget={{ ...widget, config }} editing preview />`,
  also without the required state contract.

Required correction:

- Pick one owner model and propagate it:
  - service resolver returns raw `DashboardWidgetData`, while route/builder own
    `{ id, status, data }` entries; or
  - service resolver returns an entry wrapper and renderers unwrap it explicitly.
- Update L02, L03, 480-03, 480-04, and 480-05 together.

## TASK-480 Repair Pass

  for admin GET reads and `admin_write` for admin writes/body POSTs.

  `AdminLink`, without relying on non-existent `adminPaths.*` builder APIs.
