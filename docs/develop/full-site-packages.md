# Full-site packages

Full-site packages install a complete, reviewable site through the same native
Coderso services used by individual resources. They are intended for controlled
starter-site delivery, not as a new public API or an alternative editor surface.

## Contract

`FullSitePackageV1` is a strict, versioned JSON document. Every resource is a
`{ key, desired }` seed; database IDs are resolved only during planning and
execution. The supported resource kinds are content types, forms, Page
Templates, listing templates, entries, listing queries, detail pages, Pages,
menus, and settings.

Cross-resource values use the closed shape `{ "ref": "<kind>", "key": "<key>" }`.
Only contract-owned paths accept references. Unknown fields, unsupported
reference-like objects, missing targets, cycles, duplicate keys, and resource
limit violations fail before mutation.

Package limits are:

- 8 MiB input file;
- 512 resources total and 256 resources in one collection;
- 4,096 reference edges;
- graph depth 64;
- at most 100 returned diagnostics.

Domain documents retain their own stricter limits.

## Execution and ownership

Planning classifies each seed as create, update, no-op, or conflict. An existing
natural key is managed only when a successful, non-rolled-back install run proves
the same native ID and snapshot. Otherwise the installer reports an unmanaged
conflict. Settings takeover is disabled unless explicitly requested.

Apply uses a saga with reverse-order compensation. Pages, entries, detail pages,
and menus are created as drafts; menu items, document, and appearance are written
before publish. Site-shell settings are the final reversible stage. Every
mutation stores before/after snapshots in the shared Solution Kit ledger.
Explicit rollback of a completed installation requires an exact successful apply
run, current native snapshot identity, and no later active owner. Crash recovery
may resume an exact running or failed apply run from its durable saga evidence;
all state or ownership drift still fails closed.

## FormaDom example

Generate the canonical package:

```bash
bun scripts/demo-projekty-domow.tsx
```

The output is `_docs/_DEMO/projekty-domow.site.json`. Use an existing admin/user
UUID as the explicit actor:

```bash
bun scripts/load-projekty-domow.tsx --dry-run \
  --file _docs/_DEMO/projekty-domow.site.json --actor <uuid>

bun scripts/load-projekty-domow.tsx --apply \
  --file _docs/_DEMO/projekty-domow.site.json --actor <uuid>

bun scripts/load-projekty-domow.tsx --rollback <apply-run-uuid> --actor <uuid>
```

`--allow-setting-takeover` is accepted only with `--dry-run` or `--apply` and
applies solely to package-owned setting keys. Run dry-run first, review
conflicts, keep the returned apply run ID, and use that exact ID for rollback.
CLI output is bounded JSON and does not expose raw payloads or secrets.

The example installs seven Polish Pages, six house-project entries, listing and
detail resources, a contact form, primary menu, footer Page Template, content
route, and site-shell settings. It deliberately imports no media/favicon because
the package contract has no asset/media resource kind.

## Runtime and security

This feature adds no endpoint and changes no RBAC, CSRF, or rate-limit surface.
The installed contact form continues to use the existing public Forms nonce,
validation, rate-limit, and optional CAPTCHA path. Public Page and detail
documents inherit the string locale shell (`lang="pl"` for this package).
