## Overview

Repair Product Table admin canvas parity so editors can see resolved commerce
rows before publishing. This leaf covers `BUG-00` from
`_docs/PLAYWRIGHT/REPORT_PRODUCT_TABLE_WIDGET.md`.

Current state: public rendering hydrates `product-table` blocks through
`hydrateProductTableRuntimeData()` in `core/server/publicSite.tsx`, while the
admin builder canvas renders the normalized widget block directly through
`WidgetRenderer` and therefore keeps `resolved.items=[]`.

## Scope Boundary

In scope:

- Product Table-specific admin preview hydration using the existing commerce
  query contract from `buildProductTableQueryInput()`;
- preserving the current public SSR hydration path;
- a loading/error/empty/data state in admin canvas that mirrors the same Product
  Table renderer fields;
- avoiding dirty-state overwrites when async preview results return after the
  editor has changed source/column settings.

Out of scope:

- global widget preview architecture for all commerce widgets;
- public pagination/search endpoints;
- changing commerce product CRUD behavior;
- storing resolved preview data in saved widget JSON unless the current
  persistence contract already strips runtime-only data first.

## Implementation Pseudocode

Preview request key:

```ts
function buildProductTablePreviewKey(data: ProductTableData) {
  return JSON.stringify(buildProductTableQueryInput(normalizeProductTableData(data)));
}
```

Admin preview bridge:

```tsx
function ProductTablePreviewBlock({ block }: { block: WidgetBlock }) {
  const normalized = normalizeProductTableData(block.data as ProductTableData);
  const [state, setState] = useState<ProductTablePreviewState>(() => ({
    status: "idle",
    data: normalized,
  }));

  useEffect(() => {
    const key = buildProductTablePreviewKey(normalized);
    const controller = new AbortController();
    setState({ status: "loading", data: normalized, requestKey: key });
    previewProductTableQuery(buildProductTableQueryInput(normalized), { signal: controller.signal })
      .then((result) => {
        if (controller.signal.aborted) return;
        setState((current) =>
          current.requestKey === key
            ? { status: "success", data: applyProductTablePreview(normalized, result), requestKey: key }
            : current
        );
      })
      .catch((error) => {
        if (controller.signal.aborted) return;
        setState((current) =>
          current.requestKey === key
            ? { status: "error", data: withProductTablePreviewError(normalized, error), requestKey: key }
            : current
        );
      });
    return () => controller.abort();
  }, [normalized]);

  return <ProductTableBlock data={state.data} variant="default" />;
}
```

Error handling:

- Abort stale requests on source/filter/limit/sort changes.
- Ignore late responses whose request key no longer matches current normalized
  data.
- Map known commerce query errors to machine-readable Product Table runtime
  error codes and render the existing warning box.
- Do not persist preview-only `resolved` rows when saving the page unless the
  existing page-save pipeline intentionally strips runtime data first.

## Security Contract

This leaf should prefer the existing internal admin read endpoint:
`POST /admin/api/commerce/products/query`.

- Endpoint visibility: internal admin only.
- Auth model: authenticated admin session.
- RBAC: `commerce:read`.
- CSRF: no write occurs. If the implementation creates a new POST endpoint,
  document the read-only CSRF exception or enable CSRF consistently with current
  admin API policy.
- Rate-limit bucket: existing authenticated admin/session bucket.
- Reject-unknown validation: request payload must pass `commerceQuerySchema`
  or a Product Table preview schema derived from `buildProductTableQueryInput()`.
- Anti-abuse: clamp `limit` to the Product Table schema max, reject unknown
  sort/filter fields, and avoid uncontrolled polling loops.
- Secret handling: do not write preview rows, private URLs, draft payloads, or
  errors into localStorage/debug logs.
