## Overview

The new page-editor **look** — separated `rounded-2xl border bg-card shadow-card` card + in-content `PageHeader` + "Page builder" sub-toolbar + light 280px right-docked collapsible rail + dark-correct dotted canvas — shipped (TASK-495-03) but is **inlined** in the ~5,352-line `core/admin/ui/pages/PageEditor.tsx` builder branch (gate `PageEditor.tsx:985-987`; chrome `:3373-3534`) and **hardwired to `PageDocumentV2`**. The redesign **prototype** (design source-of-truth) proves the owner's intent: **one** shared component, `_docs/_PROTOTYPE/src/components/patterns/CanvasEditor.tsx`, drives Pages (`PageEditorPreview.tsx:53-62`, `panelPosition="right"`), Page Templates (`PageTemplateEditorPreview.tsx:95-104`, right), the Screen entry-view **builder** (`CustomScreenEditorPreview.tsx:188-218`, right, title "Entry-view builder", with a data-oriented Field/Stat/Divider/Related-list/Tabs palette + a "Bound field" selector + `{{ field }}` token sections), and the Screen entry **content** editor (`CustomScreenEntryEditorPreview.tsx:123-131`, `panelPosition="bottom"`). Same look; different block range; different (data-bound) internal logic — exactly the owner's model.

This board establishes **ONE shared editor-chrome shell** and routes Pages, Page Templates, **and** Screens through it. The codebase already contains the extraction target: the **orphaned** `core/admin/ui/shared/CanvasEditor.tsx` (host-owned `canvas`/`panel`/`toolbar` slots, `panelPosition: "right" | "bottom"`, owns only `panelOpen`; docstring `:15-32` literally names "custom-screen entry-view" as a reuse target) — but it has **zero PRODUCTION importers** (the builder chrome re-inlined the look instead of consuming it; the only other references are a comment at `EditorShell.tsx:13` **and** the TASK-479-06-L06 unit spec `tests/vitest/ui-integration/canvas-editor/canvas-editor.test.tsx`, which imports the orphan and exercises its current uncontrolled built-in Hide/Show toggle + `panelTitle`/`defaultPanelOpen` — that spec is **retargeted in place by 496-01** to the new controlled read-only API, never left orphaned). ## Route decision (validated, not blindly accepted)

**Route B — one shared presentational shell that Pages, Page Templates, AND Screens render through; Screens keep their `ScreenDocumentV1` engine and only inherit the visual frame.** Verified against source:

- **NOT Route A** ("add `mode:"screen"` + flow `ScreenDocumentV1` through `PageEditor`"). Blocked by `PageDocumentV2` hardwiring: the host contract's data methods (`pageEditorHostContract.ts:192-196` `saveDocument`/`autosaveDocument`/`publish`, `:146-151` appearance, `:165-168` canvasChrome, `:141-144` palette) and the editor's entire internal canvas/layers/inline-edit/palette pipeline (`PageEditor.tsx:771-772` `useState<PageDocumentV2>`, section map / Layers / command palette) iterate `PageDocumentV2`. It would force a lossy `ScreenDocumentV1 ↔ PageDocumentV2` adapter (round-tripping the separate `ScreenFieldBinding` layer + `CustomScreenDefinitionV1..V4` envelope + list-view model through a contract with no concept of them) or type-generalizing the 5.3k-line engine. Largest scope, highest risk, discards the screen runtime/binding logic.
- **NOT Route C** ("delete the authoring stack, rebuild Screens on `PageEditor`"). Collides with both the `PageDocumentV2` coupling (as A) **and** the TASK-474 boundary test (`custom-screen-authoring-boundary.test.ts`) that intentionally fences `authoring/*` and the active screen canvas modules off `@/ui/pages`. Largest blast radius, no payoff over B.
- **Route B is realistic + prototype-literal**: a presentation refactor, not a model migration. Screens keep `ScreenDocumentV1`, the narrower block range, field-binding, the dual List/Editor view, and `ScreenRuntimeRenderer` untouched — inheriting only the frame.

### Why the shared shell MUST live at `core/admin/ui/shared/CanvasEditor.tsx`

The boundary test forces the home. `tests/vitest/ui/custom-screen-authoring-boundary.test.ts` asserts: (1) `core/admin/ui/authoring/*` imports nothing from `/pages/`, `custom-screens`, `services/pages`, `services/customScreens`, `widgets/registry`, `WidgetRenderer`, `server/`; (2) the **active** screen canvas modules (`CustomScreenEditorPage`, `CustomScreenEntryEditor`, `ScreenAuthoringCanvas`, `ScreenRuntimeRenderer`, `CustomScreenEntryCanvas`, `CustomScreenPreview`) import **no** `@/ui/pages`, `ui/pages/builder`, `@/ui/widgets`, `ui/widgets/registry`, `WidgetRenderer`; (3) `core/admin/ui/pages/*` imports **no** `custom-screens`/`customScreens`. Therefore the shell **cannot** live in `@/ui/pages` (Screens can't import it) and **cannot** live in `@/ui/authoring` (UI-only neutral — can't even reference pages). The neutral `core/admin/ui/shared/` location — which both `PageEditor.tsx` and the screen modules may legally import (the orphan already imports only `@/components/ui/button` + `@/lib/utils` + `lucide-react` + `react`) — is the **only** architecturally legal shared home. The orphan is already there: reviving it in place as the shell is the boundary-correct resolution.

## Owner decisions (authoritative)

1. **Page editor: already OK, MUST stay.** All element functionality preserved; the Pages chrome + behavior must be **byte-equivalent** after the refactor (behavior-preserving extraction only — see invariant below).
2. **Screen editor: must look like the page editor**, but uses sections & blocks to lay out a **graphical representation of a given content-type entry**, with prototype-style `{{ Field }}` bindings (e.g. `{{ Project }}`). 3. **Page Templates: de-facto the page editor for re-usable templates** applied in the page editor (shared footer/menu/etc.) so one edit propagates to many pages — already shares the page chrome; keep it (rides 496-01 for free).
4. **NO DEAD CODE (HARD MANDATE).** No unused files/paths/imports may exist. Concretely: the orphan `core/admin/ui/shared/CanvasEditor.tsx` MUST be resolved — it **becomes** the shell (wired into Pages/Templates/Screens) **or** is deleted; pick the option yielding **one** shell, **zero** orphans, and a byte-equivalent Pages result. Any authoring chrome that becomes unused after Screens adopt the shell MUST be removed. Clean architecture (YAGNI/DRY/KISS).
